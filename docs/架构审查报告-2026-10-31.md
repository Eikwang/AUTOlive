## 一、系统架构现状图景

系统为**进程/线程/队列三层模型**，与流程图 v2.9 拓扑一致：

- **进程层**：主系统进程（含 DanmakuListener 进程内托管）+ webui 前端进程 + EDTalk realtime_serve + RVC vc 服务 + fastrag server，后四者由 [service_orchestrator.py](file:///d:/AI/AUTOlive/utils/service_orchestrator.py) `ManagedProcess` 统一托管：健康轮询、就绪判定窗口、意外退出自动重拉、连续失败 red 态（crash-loop 保护）、端口冲突归因（本系统残留自动清理/外部进程抛三要素异常）、terminate→wait→kill 优雅关闭（[L34-41](file:///d:/AI/AUTOlive/utils/service_orchestrator.py#L34-L41)、[L149-192](file:///d:/AI/AUTOlive/utils/service_orchestrator.py#L149-L192)、[L296-350](file:///d:/AI/AUTOlive/utils/service_orchestrator.py#L296-L350)）；GPT-SoVITS 为进程内引擎注册 ServiceRegistry（[main.py:127-176](file:///d:/AI/AUTOlive/main.py#L127-L176)）。
- **线程层**：平台回调→`process_data`（[timer_handler.py:89-149](file:///d:/AI/AUTOlive/utils/handlers/timer_handler.py#L89-L149)）——系统消息直通 daemon 线程分发，六类互动消息经去重/限入窗口后逐条 `immediate-dispatch-*` 线程分发，同类型以独立锁串行；LLM 调用在各分发线程内并发；合成/播放为专职单线程（[audio_core.py:87-92](file:///d:/AI/AUTOlive/utils/audio/audio_core.py#L87-L92)）。
- **队列层**：两级队列（等待合成消息→待播放音频）`data_priority_insert` 统一优先级语义——`filter.priority_mapping` 18 键权重降序、编排音轨 `priority_override=500` 插队、999 复读专线单例、满载高优插队+驱逐最低优（净长度不变）、`flush_starved_playback_queue` 防饿死（[queue_manager.py:171-204](file:///d:/AI/AUTOlive/utils/audio/queue_manager.py#L171-L204)、[L312-440](file:///d:/AI/AUTOlive/utils/audio/queue_manager.py#L312-L440)）。

总评：**架构分层清晰、单源纪律（优先级表/配置矩阵/流程图守卫）已建立，治理工件密度在同规模项目中属高位**。前序批次清除了大量断链与死机制（周期触发三连退役、变声链退役、外部播放器退役等），当前主要风险从"断链"转移到"单点串行吞吐"与"观测盲区"。

## 二、稳定维

### 事实（在位机制）
| 机制 | 证据 |
|---|---|
| 子进程全生命周期托管（健康检查/自动重拉/red 态/端口冲突归因/优雅关闭） | service_orchestrator.py L149-350 |
| 前端子进程监控挂载（running_flag 复位+auto_run 重拉+训练显存互斥，ui.timer 5s） | TODOS 2026-10-23 节 #2（已闭环） |
| DB 连接池：Queue 池 + WAL + busy_timeout=5000 + SELECT 1 探活 + 积分写库 0.1×2^k×3 退避 | [db.py:32-139](file:///d:/AI/AUTOlive/utils/db.py#L32-L139) |
| LLM 通道熔断：3 次失败开路 120s + half-open 探测，per-channel 锁保护 | [llm_breaker.py:18-76](file:///d:/AI/AUTOlive/utils/llm_breaker.py#L18-L76) |
| 报警体系：六模块开关 + 飞书/企微/钉钉三通道 + 60s 模块级冷却 + 后台线程发送（5s/10s 超时） | [alarm_notifier.py:40-238](file:///d:/AI/AUTOlive/utils/alarm_notifier.py#L40-L238) |
| GPU 仲裁：直播中/EDTalk 占用/显存阈值三判据 + inproc TTS 双预留；训练 gpu_gate 门控 | [gpu_policy.py:5-81](file:///d:/AI/AUTOlive/utils/gpu_policy.py#L5-L81) |
| 线程护栏：合成主循环逐轮 try（synthesis_manager.py:86）、调度线程外层 try（2026-10-31 批）、GSV worker 护栏（V5）、翻译失败回原文不阻塞 | 各批次矩阵行 |

### 不足
1. **GPU 仲裁 fail-open**：nvidia-smi 查询失败即放行（gpu_policy.py:54），极端情况下训练在显存不足时误入→OOM 连带推理进程。有双预留缓解，但失败模式是"放行"而非"拒绝"。
2. **config 写入无原子性**：`/set_config` 远程端点整文件 `open('w')` 直写（[frontend/main.py:1326-1364](file:///d:/AI/AUTOlive/frontend/main.py#L1326-L1364)），进程中途断电/崩溃可留半截 JSON；webui/main 双 Config 形态的"静默覆盖"约束仍靠纪律维持（矩阵 §写者矩阵约束），无机制兜底。
3. **进程内托管的面**：DanmakuListener 引擎在主系统进程内，硬崩溃会带走主系统（TODOS S9 已登记隔离形态重评，商用前置）。
4. **报警观测盲区**（TODOS 已登记未实施）：伴奏线程失败仅 logger.warning（F6b）、闲时弹幕发送静默失败、编排静默窗口 busy-wait 缺打点（F6a）——直播中"无声/无字/卡画面"类故障用户可感知、系统无感知。
5. **共享态无锁**：my_global 的 global_idle_time/last_username_list 为裸全局变量（[my_global.py](file:///d:/AI/AUTOlive/utils/my_global.py)），CPython GIL 下当前操作基本安全，但切片重赋值存在理论竞态窗口，且无一致性约束提示后续维护者。

### 建议
- **S-1**：config.save 全面原子化（写临时文件+os.replace），一处公共函数收敛 webui/main 两进程写点；配合既有 .bak 机制形成双保险。
- **S-2**：gpu_policy 查询失败改为"重试一次→拒绝+告警"（fail-closed），训练入场的代价远低于误放行 OOM。
- **S-3**：将 F6a/F6b/闲时发送失败三盲区并入 alarm_notifier（复用既有模块开关与冷却机制），这是"常驻运行状态条"（D-1）数据源的补全。
- **S-4**：my_global 引入一把轻量锁或改用 queue/原子结构，成本极低，防多房间化演进后竞态放大。

## 三、高效维

### 事实
- **消费回传驱动**：播放完成回执（EDTalk push_full 返回/builtin 完成回调/pygame 结束点三路互斥）驱动取下一条，无轮询间隔（播放间隔配置已退役）——[playback_manager.py:225-244](file:///d:/AI/AUTOlive/utils/audio/playback_manager.py#L225-L244)。
- **合成串行**：message_queue_thread 单线程逐条合成（[synthesis_manager.py:44-78](file:///d:/AI/AUTOlive/utils/audio/synthesis_manager.py#L44-L78)），无并行合成池；LLM 回复生成在各分发线程并发。
- **流式合成已落地**：gpt_sovits.stream_reply 逐段落盘即入队，首段不等全文（矩阵行 59）。
- **变速零后处理**：变速迁移至 TTS 合成参数（edge-tts rate/pitch 联动、GSV speed_factor），pydub/ffmpeg 后处理链退役。
- **进程内直调**：GSV inproc 引擎免 HTTP 往返；fastrag 进程内整合。

### 不足
1. **TTS 合成是全链唯一串行点**：弹幕风暴下吞吐上限=单线程合成速度；点歌长曲/切分长回复多段会放大占用。已登记 defer：助播独立合成队列（触发条件=助播合成排队 >10s，TODOS 2026-10-26 节 #5）。
2. **翻译无缓存**：[my_translate.py](file:///d:/AI/AUTOlive/utils/my_translate.py) 无任何缓存机制，同用户刷同内容/复读场景重复调用 baidu/google API（计费+延迟+限流风险）。
3. **LLM 并发无上限**：每条弹幕一个分发线程直发 LLM，无信号量/预算控制——多房间或刷屏场景下并发 API 请求可能触发平台限流反噬（熔断器只做失败计数，不做并发节流）。
4. **DB 无归档**：danmu/integral 等表持续增长，数据分析口径已限定近 5 万条，但表本身无清理/归档任务（仅去重 live_data 桶有周期清空）——长期直播 months 后查询变慢。
5. **EDTalk 播放同步等待**：push_full 返回=消费完成，播放循环串行等待网络+推理往返；数字人推理慢时背压传导至音频队列（有 300s 静默窗口上限兜底）。

### 建议
- **H-1（低垂果实）**：翻译加 LRU 缓存（键=内容+目标语言），10 行级改动覆盖复读刷屏场景。
- **H-2**：LLM 通道加并发信号量（如 max_concurrency=3）+ 队列化等待，防限流反噬；与熔断器互补（熔断=故障隔离，信号量=负载整形）。
- **H-3**：合成并行化评估分两档——轻档=edge-tts 消息并发预合成（纯 IO）；重档=GSV 批量推理/第二实例，需 GPU 预算联动 gpu_policy。先以"实播合成排队 >5s"为触发条件，避免过早优化。
- **H-4**：DB 归档任务（danmu 按月分区或 move-to-archive 表），与"DB 驱动弹幕历史查看面"（TODOS 2026-10-22 日志批次 #1，黄金位特性）合并设计。

## 四、精准维

### 事实
- **优先级体系三层**：类型映射表（18 键）→ 编排插队 override=500 → 999 专线单例；满载四规则+插队驱逐语义经测试锚定（test_audio_playback_review.py 四示例逐行）。
- **消费回传精准匹配**：编排实例 choreo_step_id 精确匹配，未透传路径退回 type+content 归一化容差（O6/O9）；三路消费点互斥不双报。
- **入口秩序固定**：黑名单前置拦截（先于去重/限入/分发，不占窗口名额痕迹零残留）→ 去重 → 限入窗口 → 过滤链 → 关键词中枢（keyword_hub 统一判定 song/keymap/local_qa/reread）。
- **丢段可见面**：切分消息 split_group 组绑定，四丢弃/取代点附注"第几段/共几段"（UI-16 批次 #3 根修）。
- **变量断链清零**：{last_username}/{user_num}/{time} 及 [|\] 随机段全链接线（2026-10-31 三批次）。

### 不足
1. **choreo_step_id 回退路径的固有模糊**：同内容重复触发且未透传实例号的极端场景仍可能误配/漏配（O9 声明为容差回退）——当前生产点已全部透传，风险收敛但未归零。
2. **未识别类型静默丢弃**：消息队列对未识别类型"队尾+满则丢弃"无计数观测（ENG E-1 队列深度/丢弃计数可观测，TODOS 2026-10-20 #3 pending）——动态文案 type 断链（trends_copywriting）即此类问题的实例，修复靠审查而非机制。
3. **礼物计价连击少计**：B站/快手连击语义与差值去重不匹配，修复依赖真实样本采集（TODOS 2026-10-22 弹幕批次 #3）。
4. **助播与数字人重叠无避让**：同刻重叠为已接受设计属性（D9），实播投诉成立再评估——精准维的已知取舍。

### 建议
- **P-1**：队列落一个"丢弃计数器"（按丢弃原因分桶：满载/未识别/999 舍弃/限入/去重），webui 状态条透出——把每次架构审查的"断链考古"变成运行期可见指标，这是精准维投入复利化最高的一项。
- **P-2**：choreo_step_id 透传完整性加守卫测试（枚举全部入队生产点断言携带），防新增生产点退回容差匹配。
- **P-3**：连击样本采集（fixture）后做计数语义对齐，礼物计价直接影响答谢门槛与积分金额榜精度。
