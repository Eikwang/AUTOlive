## Problem Statement

AUTOlive 的三个音频能力目前依赖三个独立外部项目（GPT-SoVITS、RVC20240604Nvidia、AICoverGen），需要手动启动服务、手动对配置、凭记忆维护启动顺序。本次整合把它们收编为系统一等公民：TTS 内部调度（AI对话-文本转语音）、实时变声（AI对话-变声，运行时热切换模型）、声音训练（数字人-训练声音，两条训练流）、一键翻唱（高级功能-点歌模式）。

钢人框架（来自第二意见）：这不是"集成三个项目"，而是给中文个体主播建一条**声音身份生产线**——录音 → 训练主播自己的声音模型 → 同一声音身份自动流入 TTS、实时变声、翻唱三个消费端。三个项目是生产线的三台机器，AUTOlive 才是产品。

## Demand Evidence

- 用户（其他主播，免费使用中）的原话："手动搭链路，很痛苦"——他们已经在跑 GPT-SoVITS 和 RVC，缺的是运行时链路，不是能力本身。
- 产品阶段：有用户、未付费。真实用户在日常使用整套系统。
- 创始人已做过不加干预的用户观察并有意外发现（具体内容待补，见 Open Questions 第 1 条）。

## Status Quo

用户现状：手动搭链路——自己装 GPT-SoVITS/RVC，每次开播按记忆顺序启动、手改配置文件、端口对接靠试错。代价：开播准备时间、崩溃后无人会救、声音能力与直播系统脱节。

系统现状（代码核实）：
- TTS：`utils/audio_handle/my_tts.py` 走 HTTP 外部 API，`gpt_sovits` 配置指向 `127.0.0.1:9880`（外部管理）。
- 变声：`frontend/ui/tabs/svc.py` 配置的是旧 so-vits-svc 外部服务（`127.0.0.1:1145`，`so_vits_svc.enable=true`，指向 `E:\so-vits-svc`——**旧服务可能仍在使用**）。
- 点歌：`frontend/ui/tabs/choose_song.py` 只做本地音频相似度匹配，无翻唱能力。
- runtime312（EDTalk 共享环境）已通过 users.pth 注入 6 个 GPT-SoVITS 路径——环境早已纠缠。

## Target User & Narrowest Wedge

目标用户：中文个体主播（自己就是第一个）；扩展对象是正在免费用系统的真实主播。
最窄楔子（会话裁决：先服务好一个用户）：**分两步交付给同一个真实用户**——
- 第一步（P1 后）：装"基础链路包"，验收标准是"不靠作者本人也能开播"（系统内建声音可用，无声音克隆）；
- 第二步（P2 后）：补装声音克隆能力（训练声音页），同一用户用自己克隆的声音开播。
观察其真实使用后再决定扩展方向。

## Constraints

- 单人开发者 + AI 辅助开发；Windows 11 单机部署。
- GPU 争用：EDTalk 训练/推理已占卡。**GPU 优先级策略（本期新增裁决）**：直播关键路径（EDTalk 实时推理、TTS、变声）> 背景任务（翻唱生成、音频训练）；音频训练/翻唱启动前探测——**探测条件 = 直播运行中 OR EDTalk 训练占用中**，任一命中则训练拒绝启动并提示、翻唱排队等待；探测同时检查显存余量（低于阈值如 4GB 亦拒绝，与线框草图② 的"GPU 占用检查：edtalk 空闲/显存余量"对齐）；EDTalk 训练进行中允许变声/TTS 推理（推理显存占用小），实测余量在 P2 工程审查确认。
- 既有整合范式必须复用：EDTalk 的"复制为唯一副本 + 子进程编排 + 配置驱动 UI + 步骤清单训练页"。
- 直播链路不能被阻塞：翻唱是分钟级任务，必须异步。

## Premises（会话中逐条确认，含两处修订）

1. **内部调度 = AUTOlive 托管子进程生命周期**（自动拉起/配置注入/健康检查），非同进程 import——与 EDTalk 范式一致。**修订（第二意见证实）**：此前提对 GPT-SoVITS 成立（api_v2.py 是标准 API 服务），对 RVC 实时变声**不成立**——`gui_v1.py` 全文无任何 RPC 面（已 grep 验证：无 Flask/FastAPI/WebSocket/Gradio）。裁决（用户选定）：RVC 走**包裹式服务**——AUTOlive 自建薄推理服务（自有子进程 + 声音设备 I/O，复用 `tools/rvc_for_realtime.py` 推理类，版本锁定），实现运行时热切换，不维护上游 fork。
2. **共享模型**：**修订（用户同意降级）**——放弃通用模型仓库抽象，只建一个 AUTOlive 管理的 RVC 模型目录（`models/rvc/`）供 RVC+AICoverGen 共用；GPT-SoVITS 六个权重族（v2/v2Pro/v2ProPlus/v3/v4）只有它自己消费，留在原目录。
3. GPT-SoVITS 训练 + RVC 训练统一为"数字人-训练声音"一页两条流（tab 分节，共享数据集输入）。
4. RVC 变声（P2）就绪后，现有 `so_vits_svc` 配置退役：默认关闭、前端隐藏旧设置卡、保留配置数据不删除（P1 不动旧配置，避免批次间能力真空）。
5. 点歌模式保留现有匹配播放；AICoverGen 翻唱为异步增强（队列化，不阻塞直播链路）。
6. 交付物包含给一个真实用户的安装包；去硬编码路径（D:\AI\... 收敛为根目录配置 + 环境变量解析）纳入本期。

## Cross-Model Perspective

第二意见（Claude 子代理冷读，Codex 因 provider 模型 400 不可用）：

- **钢人**：声音身份生产线（见 Problem Statement）。
- **最有信息量的回答**："手动搭链路，很痛苦"暴露用户已拥有全部能力，缺的是运行时链路（启动顺序/崩溃恢复/端口对接）；而计划中工作量最大的两项（两个训练 UI）服务的是"每个声音只跑一次"的环节——**痛点和投入错位，训练页应排在链路稳定之后**。一个用户的验收标准 = "不靠作者本人也能开播"。
- **被证伪的前提**：前提 1 对 RVC 不成立（已验证并按用户裁决修订）；前提 2 通用仓库是过度设计（已按用户裁决降级）。
- **48 小时原型**：去硬编码（根目录配置 + 环境变量）+ 启动器按序拉起 + 端口探活（复用 EDTalk 探活代码）+ 进程监督。跳过全部训练页。验证指标：用户从双击到开播出声的分钟数 + 作者被求助次数。

## Approaches Considered

- **A. 运行时链路优先（选定）**：完整范围 + 痛点排序，P1=运行时链路+安装包 → P2=变声+SoVITS 训练页 → P3=RVC 训练页+翻唱。每批独立验收。
- B. 按页面归属平铺（用户原始顺序）：训练页最早可用，但最重工作先行，"服务一个用户"推迟到最后——痛点/投入错位，否决。
- C. 声音身份生产线（横向重构）：围绕注册表重构三端——**大抽象否决**；其轻量内核（声音档案映射，见 P2 ③）以 config 数据节形式保留，不构成对否决项的翻案。

## Recommended Approach

**方案 A**，三批交付（每批可独立验收、独立产生价值）：

- **P1 运行时链路**：
  ① GPT-SoVITS api_v2 子进程托管（TTS 内部调度，设置项并入 tts.py）；
  ② 去硬编码（根目录配置解析；**含 users.pth 收编**：GPT-SoVITS 路径注入改由 AUTOlive 启动器按根目录配置向子进程注入（PYTHONPATH/env），不再依赖手工维护的 users.pth）；
  ③ 侧边栏服务状态常驻条（每托管进程一个胶囊：健康/日志尾/重启/**崩溃自动重拉带失控防护**——同一进程连续 3 次拉起失败后停止自动重拉、胶囊置红 + 日志尾标红，此即告警形态（无独立通知渠道，不引入新通知系统），防 crash loop 刷爆日志）；
  ④ 共享 RVC 模型目录建立（`models/rvc/`）；
  ⑤ **安装包构建**：启动器（按序拉起+端口探活，复用 EDTalk 探活代码）+ 内嵌 Python 运行时打包方式 + 模型资产分发方式（见 Open Questions 第 5 条清单，含虚拟声卡驱动的静默安装方式）。
  P1 完成 = 基础链路包可装机（楔子第一步，见 Target User）。
- **P2 变声 + 第一条训练流 + 声音档案**：
  ① RVC 包裹式实时变声服务（**热切换机制假设**：切换期间音频流连接不中断，允许 ≤1s 静音间隙（模型卸载/加载），切换间隙音频静音丢弃不缓冲；`rvc_for_realtime.py` 推理类是否支持进程内换模在 P2 工程审查验证，若不支持则降级为"快速重启切换"并修订成功标准）；**输出路由**：默认输出到虚拟音频设备（如 VB-Cable）供直播管线/OBS 采集，保留物理扬声器监听选项；TTS 文件播放路径不变，变声作为可选处理节点（音频桥机制细节 = Open Questions 第 2 条，阻塞 P2 验收）；**延迟目标：端到端 ≤500ms**（RVC 实时典型值），P2 验收含实测，含与 EDTalk 并存时的性能评估；
  ② GPT-SoVITS 训练页（数字人-训练声音，步骤清单形态复用 train_streamer）；
  ③ **声音档案（轻量注册表，纳入 P2）**：config.json 新增 `voice_profiles` 数据节——档案 ID → {GPT-SoVITS 模型对, RVC 模型/index, 参考音频} 映射；训练页末步"导出为声音档案"写入该节；TTS/变声/翻唱三端的选择器读同一节。这是 config 数据约定，不是通用抽象层。
  P2 完成 = 声音克隆能力补装给同一用户（楔子第二步）。
- **P3 第二条训练流 + 翻唱**：
  ① RVC 训练流并入训练声音页（产出 .pth+.index 直接入 `models/rvc/` 并可挂接声音档案）；
  ② AICoverGen 翻唱队列（点歌无本地结果 → 排队翻唱 → 完成后弹幕回播，成品沉淀 `song/covers/` 永久复用）。**异常路径**：失败向直播间推送失败文案（复用 `match_fail_copy` 机制）并注明原因；自动重试 1 次后放弃；单任务超时上限 10 分钟；队列长度上限 5，超出时提示"点歌排队已满"。**受理反馈（有意设计）**：点歌成功入队时静默受理、不推确认文案——完成回播/失败文案/排队已满是仅有的三种直播间反馈（降低弹幕互动噪音；如后续需要"已排队第 N 位"提示属增强，不在本期）。

## Open Questions

1. 创始人已观察过真实用户并有意外发现——具体内容本会话未记录，需在装机观察时补齐（三句话即可）。

4. 合规：中文平台 AI 主播/变声的备案与标注要求。
5. **模型资产清单（安装包分发）**：GPT-SoVITS 底模族（v2/v2Pro/v2ProPlus/v3/v4，按需选装，数 GB 级）、RVC 底模（hubert_base/rmvpe 等，约 1-2 GB）、AICoverGen 分离模型（MDX/UVR，数 GB）、**虚拟声卡驱动**（P2 输出路由依赖，如 VB-Cable 或替代方案——选型与许可核查并入 Open Questions 第 3 条，静默安装方式随安装包定案）——逐项列体积与许可，分发方式（预打包进安装包 vs 安装器下载 vs 首次运行下载）随资产清单在 P1 ⑤ 一并定案；Distribution Plan 不再单独裁决此项。
6. 环境策略默认案（P1 工程审查确认）：GPT-SoVITS 托管进程复用 runtime312（路径注入已存在且兼容）；RVC 包裹服务跑在 RVC 自带 runtime 内（依赖现成、零安装风险）；AICoverGen 复用 RVC runtime 或独立 venv（P3 定）；安装包体积与依赖冲突影响随环境策略定案。

## Success Criteria

- 一个真实用户从双击安装包到开播出声 ≤ 30 分钟，全程无作者介入（基础链路包，P1 验收）。
- TTS 链路无外部手动服务依赖（AUTOlive 托管生命周期，崩溃自动重拉带失控防护）。
- 变声模型运行时热切换：音频流不中断，允许 ≤1s 静音间隙；端到端延迟 ≤500ms（P2 验收）。
- 训练完成的声音以声音档案形式在同一界面被三端（TTS/变声/翻唱）直接选用（P2/P3 验收）。
- 翻唱失败/排队满有确定的直播间表现，不静默失败（P3 验收）。
- 作者被求助次数显著下降（基线：每次装机都需要作者到场）。

## Distribution Plan

给第一个用户的交付：Windows 安装包（启动器 + 内嵌式 Python 运行时 + 模型资产，分发方式随 Open Questions 第 5 条清单定案）。分发先人工（网盘/现场装机），CI 打包流程在 P1 落地后评估（GitHub Actions 构建，人工发布）。WEB UI 默认绑定收敛为 127.0.0.1（联动 TODOS 暴露面收敛项）。

### R3-1 — completeness

**Problem**

> GPU 优先级策略只定义了启动准入：Constraints 规定'音频训练/翻唱启动前探测'，但已在运行的背景任务在直播开启或 EDTalk 训练开始时如何处置无任何定义——继续运行则与'直播链路不能被阻塞'直接冲突（显存竞争可致直播关键路径劣化/失败），让路/暂停/终止/有意放行均未写明。'先启动后台任务、后开播'这一顺序落在准入探测的覆盖范围之外。

**Remedy**

> 为运行中的背景任务定义与新关键路径冲突时的行为（如翻唱任务可中断回队、音频训练不可中断则写明显存余量预留与风险声明），或明确'只管准入、运行中不干预'是有意接受的风险并说明理由。

### R3-2 — completeness

**Problem**

> 安装包构成（P1 ⑤）只列启动器、内嵌 Python 运行时、模型资产（OQ5 清单）、虚拟声卡驱动与 ffmpeg（Dependencies），三个被整合项目（GPT-SoVITS / RVC / AICoverGen）的程序本体如何随包分发未写明。Constraints 声明复用 EDTalk 整合范式（含'复制为唯一副本'），但三个批次没有任何一项安排这三个项目的代码入库复制或分发归属；P1 验收是'基础链路包可装机'，缺程序本体的分发方案装不了机。

**Remedy**

> 写明三个项目代码的归属与分发方式：按 EDTalk 范式复制为唯一副本入 AUTOlive 仓库、随安装包分发（挂到对应批次与 P1 ⑤ 打包清单），或采用其他方式并写明理由。

### R3-3 — completeness

**Problem**

> 楔子承诺'分两步交付给同一个真实用户'（Target User），第二步是 P2 后'补装声音克隆能力'，但补装的形式未定义：重跑完整安装包、增量安装器、还是启动器按需拉取 RVC 模型与包裹服务。OQ5 的分发方式裁决只有一个口径（预打包进安装包 vs 安装器下载 vs 首次运行下载），未区分第一步基础链路包与第二步补装的安装包构成差异——两步交付的操作路径无法按现文验收。

**Remedy**

> 在 OQ5 或 P2 写明补装形式（如同一安装器支持分步选装，与 OQ5 分发方式裁决合并定案），使楔子第二步可操作、可验收。
