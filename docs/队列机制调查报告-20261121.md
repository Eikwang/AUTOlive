## 一、系统全景：实际是「三层缓冲 + 两条有序队列 + 一个播放器内部队列」

```
各 handler（弹幕/礼物/进场/助播/闲时/编排…）
   │ put_to_queue → data_priority_insert("等待合成消息")
   ▼
① message_queue（待合成消息队列，权重降序有序数组，max_len=12）
   │ 合成线程 message_queue_thread（synthesis_manager.py:51）
   │   pop 前过「合成背压门」synth_gate_wait_s
   ▼
my_play_voice → TTS 合成（tts_type=none 直通）
   │ 成功 → data_priority_insert("待播放音频列表")
   ▼
② voice_tmp_path_queue（待播放音频队列，权重有序，max_len=4）
   │ 消费线程 only_play_audio（playback_manager.py:1001）
   │   pop 前过「组原子门/点歌窗口门/念白单飞门」
   ▼
┌─ EDTalk 路由：push_full(wait_flight=True)，飞行等待=播完才返回（串行）
└─ 本地路由：builtin 播放器 play() 提前移交
        ▼
   ③ audio_json_list（播放器内部缓冲队列，queue_max=2，满载阻塞背压）
        │ 播放器内部 play_audio 循环逐条同步播放（builtin_play_center.py:398）
```

### 四个队列参数的实际键位与当前值

| 用户参数名 | 配置键 | 当前值 | 实际作用点 |
|---|---|---|---|
| 播放器缓冲队列上限（背压） | `audio_player.queue_max` | **2** | builtin 播放器 `play()` 满载阻塞（builtin_play_center.py:832-841） |
| 待处理队列长度 | `filter.message_queue_max_len` | **20**（原 12，优化批次 E1 调整） | message_queue 满载判定（queue_manager.py:821） |
| 待播放队列长度 | `filter.voice_tmp_path_queue_max_len` | **4** | voice_tmp_path_queue 满载规则 1-4 |
| 待播放队列压力 | `play_audio.synth_gate_depth` | **4**（原 2，优化批次 E1 调整；budget>0 时退为回退口径） | 合成背压门条数门限模式 |

新增配置键（优化批次）：`play_audio.synth_gate_budget_s=15.0`（秒数预算门控，>0 优先于条数门限）、`filter.message_queue_replace_same_priority=true`（消息队列同权重顶替开关）。

另有 `filter.voice_tmp_path_queue_min_start_play=0`（首播阈值门当前实质关闭，E2 flush 兜底在 queue_manager.py:342）。

**参数语义核对**：
- 「播放器缓冲队列上限=2 → 1 播放 + 1 等待即不能再进入」：**与实现一致**。`play()` 在内部队列 ≥2 时阻塞等待消费完成（对齐"阻塞式背压"义务）；但它阻塞的是消费线程 only_play_audio 的移交动作，间接也阻塞了整条消费链。

## 二、待合成消息队列（message_queue）实际机制

### 2.1 入队与排序（queue_manager.py:550-744，锁内完成）

- 权重单一源 `audio_priority.entry_priority`：`priority_override`（编排 500）优先，否则查 `filter.priority_mapping`；未识别 type 排队尾。
- **song 切片段**：强制队尾追加不插队（seq 有序保序），满载豁免（不丢段）。
- **动态文案分段（trends_copywriting + split_group）**：2026-11-21 批次新增，同样队尾追加不插队 + 满载豁免 + 不占普通容量（分账编组，`_normal_queue_len` queue_manager.py:592-600）。
- 普通条目：从队尾向前找第一个权重 ≥ 新条目的元素插其后（同权重 FIFO）。

### 2.2 满载语义——与你的设计预期存在一处关键差异

| 场景 | 实际行为 | 观测桶 |
|---|---|---|
| 队满 + 新条目插在队尾（低优/未识别/同权重堆积） | 直接丢弃 | `message_queue_full` |
| 队满 + 新条目可插队（权重高于队内条目） | 插队 + 驱逐队尾最低优普通条目（song/文案段受保护不驱逐） | `message_queue_evict` |
| 队满 + song/文案切分段 | 豁免，仍接队尾（队列可暂时超限，消费回落） | — |

**差异点**：你预期「消息队列产生积压时，新入队的消息**顶替最旧的同权重消息**」。调查时实际实现中**同权重顶替只存在于待播放音频队列**（规则 2）；待合成消息队列是 **drop-only + 插队驱逐队尾** 语义（注释明确：`等待合成消息分支维持既有 drop-only 语义（设计仅规定待播放队列，不越权改动）`）。推论：**同权重消息连发打满队列时，后者不会顶替前者，而是自己被丢弃**——assistant 分段（权重 40）连发正是此场景（见第四节根因）。
>
> **✅ 已由 2026-11-21 优化批次 F1 修复**：消息队列补齐同权重顶替（开关 `filter.message_queue_replace_same_priority`，默认开）——队满同权重堆积时新条目顶替最旧同权重条目、接组尾（净长度不变，组内 FIFO 保序）；关闭开关回退 drop-only。字符串落盘值按字面解析（`"false"` 不会误判为 True）。

### 2.3 消费与背压

- 合成线程 pop 前过合成背压门：待播放普通条目深度 ≥ `synth_gate_depth`(2) 时暂停出队，等消费出队回执 `notify_synth_gate` 唤醒（1s 轮询兜底，synthesis_manager.py:61-74）。
- 豁免面：song 切片段 / 权重 ≥500（复读、编排 override）/ reply_link 命中念白配对 pending / 非 dict 防御（queue_manager.py:262-282）。**assistant 分段不豁免**。
- TTS 失败：报警、本条作废、不回队不重试（synthesis_manager.py:898-907）。
- **结构性结论**：背压门 + 消费回传使「消息队列排水速率 ≈ 播放速率（一条音频播完才腾一个槽）」。消息队列的 12 个位置实际充当的是"播放速度差缓冲"，而非合成速度缓冲。

## 三、待播放音频队列与消费回传机制实际实现

### 3.1 消费回传（每完成一次消费才消费下一个）

- **EDTalk 路径**：`push_full(wait_flight=True)` 阻塞至本句播放完成（时长×1.05 + buffer 轮询）才返回，消费循环才 pop 下一条——**完整串行，与预期一致**（song 切片段豁免飞行等待，playback_manager.py:881-887）。
- **本地路径**：消费循环 `play()` 提前移交到播放器内部队列后立即返回，**不等播放完成**；真正的"逐条消费"发生在播放器内部循环（同步 `_play_item`）。消费回执 `report_consumed` 在**真实播放完成点**上报（audio_core 完成回调），不在移交点（W3 根修防双计，playback_manager.py:1155-1170）。即「进入播放器即视为消费完成」在**队列槽位释放**意义上成立（移交即腾槽），在**消费回执**意义上不成立（回执=真实播完）。
- 消费出队后统一发两个回执：`reply_gate_track_popped`（念白配对登记）+ `notify_synth_gate`（唤醒合成背压门），playback_manager.py:1038-1046。

### 3.2 满载语义（规则 1-4，queue_manager.py:766-924，全部锁内）

- 规则 1 未满：按权重插入（同权重接组尾 FIFO）。
- 规则 2 队满 + 同权重组存在：**取代该组组首（最老）条目**，新条目接组尾 —— 即你预期的「同权重顶替最旧消息」，**仅在待播放队列实现**。
- 规则 3 队满 + 新权重 > 最低优：插入后驱逐最低优组组首（最老）。
- 规则 4 队满 + 新权重更低：丢弃新音频。
- **song 切片段 / 动态文案分段满载豁免**（接组尾，序列不可丢）；规则 2/3 的同权重/最低优候选**排除背景流切片**，但**不排除其它切分组（assistant/comment 等）**——这些组的段仍可被规则 2/3 驱逐（见 5.1 差异）。
- 连续对话 talk 条目：入待播放队列时若积压 ≥2 直接清空只播最新（`_maybe_discard_pending_for_talk`，queue_manager.py:443-471，切分段/流式分句豁免）。

## 四、「长回复切分」丢弃告警根因链（本次告警频发的直接解释）

告警产生点：[synthesis_manager.py:562-594](file:///d:/AI/AUTOlive/utils/audio/synthesis_manager.py#L562-L594)。`text_split_enable=true` 时按句切分，每段带 `split_group` 逐段入队；入队前做容量预检（排除 trends_copywriting），余量不足即打 warning。

**根因链（结构性，非偶发）**：

1. **生产突发**：`assistant_anchor_text` 经助播路由产生，权重 40；每条回复被切分为 4 段（本次日志样本），且助播分句会连续多条入队。
2. **消费串行**：背压门(2) + 消费回传（一条播完腾一槽）使消息队列排水速率被播放时长钳制；每条 assistant 消息 = 4 段 ≈ 4 个播放周期。
3. **同权重无顶替**：消息队列 drop-only 语义下，同权重（40）assistant 分段堆积到队尾后无法被新分段顶替——新分段插入位 = 队尾 = 满载丢弃。
4. **容量 12 过小**：两条 4 段消息 + 少量常规消息即触顶。
5. **告警口径偏差（放大观感）**：预检告警用 `len(message_queue)` 总长度（含 song/文案段，synthesis_manager.py:577），而实际满载判定用分账口径 `_normal_queue_len`（不含 song/文案段）。点歌/动态文案占用队列时，告警会**虚报丢弃风险**；反之预检通过后逐段入队仍可能触发真实丢弃（`message_queue 已满，数据丢弃：…〔长回复切分段：第 x/y 段〕`）。另外"超容部分将被丢弃"是简化表述——若队尾存在低优条目，实际路径是**插队并驱逐其它条目**（`message_queue_evict`），并不一定丢弃本批分段。

## 六、运行表现总结与风险清单

1. **丢弃是结构性的，不是偶发**：串行消费链（背压门 2 + 消费回传 + 播放器缓冲 2）下，消息队列排水速率 ≤ 播放速率。assistant 每条回复产 4 段、连发即触顶 12；同权重又无顶替 → 必然 `message_queue_full`。**告警本身工作正常**（预检提前暴露 + 分段上下文可定位），暴露的是容量与速率失配。**✅ 已由优化批次缓解**（容量 20 + 门限 4/预算 15s + 同权重顶替，见 §八）。
2. **弹幕问答编组存在遗弃缺口**：组开始消费后不被插队 ✓，但组内段在两队列满载时均可被丢弃/驱逐（assistant/comment 组不在分账豁免面），"完整处理并消费"的预期未闭环。**✅ 已由优化批次 S1 修复**（组进入消费流程后其切分段两队列满载不丢不驱逐、不参与顶替候选）。
3. **消息队列缺同权重顶替**：与你描述的优先级队列机制（"新入队消息顶替最旧同权重消息"）不符；该机制只存在于待播放音频队列。代码注释显示这是有意为之（"设计仅规定待播放队列"），但与当前产品预期不一致，需要产品裁决。**✅ 已由优化批次 F1 落地**（裁决结果：开启，做成开关）。
4. **告警口径偏差**：预检告警用总队列长度（含 song/文案段），与分账满载判定口径不一致，点歌/文案在场时会虚报。**✅ 已由优化批次 E3 修复**（预检改用分账口径单源 `message_queue_normal_len`）。
5. **本地路径下"待播放队列压力"门有观测盲区**：门控只数 voice_tmp_path_queue，播放器内部队列（queue_max=2）才是本地路径真实缓冲点；本地路径下门几乎不触发，积压体现在播放器内部与消息队列。**✅ 已由优化批次 E2 修复**（门控深度叠加播放器内部队列普通条目）。

## 七、可选修复方向（按影响排序）——已全部裁决并落地，见 §八
